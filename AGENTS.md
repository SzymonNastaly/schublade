# Agent instructions

Schublade is a self-hosted document archive that runs as one Cloudflare Worker. TanStack Start serves the interface, D1 holds the relational records, R2 holds the original files, AI Search indexes the text, and a Workflow runs ingestion. Read this file before you change code. The `cf` command-line interface and `cloudflare.config.ts` are newer than most training data, so look up what you are not sure of (see [Documentation lookup order](#documentation-lookup-order)).

`cloudflare.config.ts` is the source of truth for bindings, and `src/database/schema.ts` is the source of truth for tables.

## Rules, most important first

1. **Fail closed.** Every browser request needs a valid Cloudflare Access assertion. When `ACCESS_TEAM_DOMAIN` or `ACCESS_AUD` is blank, the Worker rejects every request with 403. Never add a fallback identity, a demonstration user, or a path that skips `requireAccess` in production code. The only exemption is `VITE_ACCESS_DEVELOPMENT_EXEMPTION`, which exists only under `import.meta.env.DEV` and is absent from builds.
2. **Every resource binding needs an identifier.** `cf deploy` provisions a new, empty resource for any D1 or R2 binding without an identifier and never records it. Identifiers come from the git-ignored `schublade.deploy.json`, which `pnpm run provision` writes. `cloudflare.config.ts` throws in every build mode while an identifier is missing. Keep that check, and extend it when you add a resource binding.
3. **Never call billed Cloudflare services in tests.** Workers AI, Browser Run, Images, and AI Search bill per request. The workerd test project sets `remoteBindings: false`, and tests replace those bindings with recorded responses.
4. **Follow the naming specification.** The specification reads:

   Every identifier in this repository, across files, scripts, directories, functions, variables, classes, database columns, bindings, commits, and branches, must use precise professional vocabulary. Choose the exact technical term a 1972 IBM systems engineer would write in a formal specification. Avoid slang, casual shorthand, abbreviations, metaphors, or conversational idioms. For example, a script that provisions infrastructure is `provision_environment.ts`, not `setup.ts`, and a module that coordinates client state is `archive_coordinator.ts`, not `archive_hub.ts`.

5. **Use `cf`, not `wrangler`.** Wrangler cannot read `cloudflare.config.ts`. Do not create `wrangler.jsonc` and do not run `wrangler` commands.
6. **Commit straight to `main`.** Schublade uses no branches and no pull requests. Work in the main checkout on `main`, subagents included, and create no feature branch and no git worktree. Each commit is one change that passes `pnpm check`, with an imperative subject and a body that explains why. Push only when the user asks. The pre-push hook runs `pnpm check`. Never bypass it.
7. **Keep the test suite lean.** `pnpm check` finishes in under 60 seconds. Write one test per behavior, call the code as its users do, and assert literal values from the test or from `test_fixtures/documents/expected_extraction.json`. Use the workerd project only for code that needs the Workers runtime, such as bindings or WebAssembly. No snapshot tests and no browser tests.
8. **The Moondream binding returns an event stream.** `env.AI_RUNTIME.run()` for `@cf/moondream/moondream3.1-9B-A2B` returns server-sent events even without `stream: true`. Every `chunk.answer` repeats the full answer so far, so `parseMoondreamEventStream` reads the stream line by line and keeps the last one. A `finish_reason` of `length` means the page never finished, so its text is not kept.
9. **Generate migrations with drizzle-kit and apply them with `cf`.** Never run `drizzle-kit push` or `drizzle-kit migrate`, and never edit an applied migration.
10. **`cloudflare:workers` is server-only.** Import it only from server functions, the Worker entry, Workflows, and Durable Objects, never from a component.
11. **Edit the human-facing document only when the user asks.** README.md is otherwise written outside coding sessions. When a change makes it wrong, list the edits it needs in your report.

## Things that will bite you

- **The interface draws only from its theme and its controls.** `src/styles.css` switches off Tailwind's default palette, so `bg-white` produces no style, and `pnpm lint` rejects a class the theme does not define. A new colour is a token in `@theme`, and a class list held in a variable needs a name that `eslint.config.js` matches, such as one ending in `Classes`. Only `src/interface/controls/` may import Base UI. Blue means the archive, orange means Failed documents, and green means Settings, so colour a panel by the section it belongs to.
- **Three widths matter.** Below `md` a page uses the phone navigation and one column. From `md` the header shows the Documents tab and the Failed documents and Settings links. From `lg` the panel column sits beside the content. A list or table inside `ListFrame` chooses its columns with container variants such as `@xl:`, because its width depends on the panels as well as the window.
- **Configuration modes.** Builds evaluate `cloudflare.config.ts` in `production` mode or the `--mode` they receive. `cf dev` evaluates it in `development` mode, and `cf workers types` evaluates it without a mode. Only build modes require the identifiers in `schublade.deploy.json`.
- **AI Search has no local simulation.** Every local mode binds `SEARCH_INDEX` to the remote AI Search instance `schublade-development`, which must exist on the signed-in account with the same four custom metadata fields as a provisioned instance. A dev server therefore never writes into the index of a deployment, but the local D1 database and that shared index can disagree. Searches and uploads against it are billed.
- **Await `SEARCH_INDEX.items` before calling it.** In development, the remote binding answers over RPC, and `env.SEARCH_INDEX.items.list()` fails with `The RPC receiver does not implement the method "list"`. `await env.SEARCH_INDEX.items` first, as `document_indexing.ts` does. A deployed Worker returns the object itself, so the await costs nothing there.
- **AI Search facts the search relies on.** An upload under an existing item name replaces the item and keeps its identifier. A `datetime` metadata field accepts `2026-09-22T00:00:00Z`, stores milliseconds, and filters correctly with ISO 8601 strings, not with Unix seconds. While an item reindexes, its old and new chunks can both match, so results are grouped by item name. Indexing an upload took 73 to 145 seconds on the development instance when 12 arrived together, so a document archived a moment ago is not yet searchable. Every search disables the similarity cache, which would answer a repeated query without the documents indexed since.
- **A new route needs a regenerated route tree.** Only `pnpm dev` and `pnpm build` rewrite `src/routeTree.gen.ts`, and until then `tsc` rejects the path that the new file passes to `createFileRoute`. Without a dev server, regenerate it with `node --input-type=module -e 'import { resolveConfig } from "vite"; import { tanstackStart } from "@tanstack/react-start/plugin/vite"; await resolveConfig({ configFile: false, root: process.cwd(), plugins: [tanstackStart()] }, "build")'` and commit the result with the route.
- **URL search parameters are parsed in `parseSearchString`.** TanStack Router merges every parameter it parses into the validated search of each route, so `validateSearch` alone cannot drop an unknown or unreadable one, and the default parser reads `1.50` as a number. `src/router.tsx` therefore passes `parseSearchString` and `composeSearchString` from `search_criteria.ts`. The router keeps only the archive criteria that `parseSearchString` returns, so the archive loader passes its search straight to `retrieveDocuments`, which refuses any other key. A new search parameter must pass through `parseSearchString`, and the archive loader must then drop it.
- **A document is stale while its updated_at exceeds its indexed_at, or its indexed_at is null.** The index step reads updated_at before anything else, uploads, and stores that revision only while updated_at still holds it. When the revision changed during the upload, AI Search may have accepted an older upload last, so the step clears indexed_at and raises updated_at, which keeps every overlapping upload from recording its revision too. Every update raises updated_at by at least one second, so a revision written in the second of an upload still counts as stale. A write that changes nothing AI Search reads, such as recording indexed_at, sets `updatedAt` to its own column, or the backfill uploads the document again. A merge or rename marks its documents stale with `succeedingModificationTime()` instead of uploading each one.
- **A content is the SHA-256 of a file's bytes, and the archive holds each content once.** The `contents` table names every byte sequence the archive has received and the document that holds it, and `documents.original_sha256` names the content a document shows. `archiveContent` in `document_upload.ts` is the one rule for every arrival, from the browser, a token, mail, or `PUT /api/v1/contents/{sha256}`: bytes a document holds answer `already_archived` before any write. Otherwise the document row and the content claim go into one D1 batch, which D1 runs as one transaction, and the claim is read back, so the loser of two concurrent uploads removes its own row and answers with the winner. Deleting a document passes its content to the oldest other document with the same `original_sha256`, which an archive from before migration 0006 can hold, and otherwise sets the content's `document_id` to null, so the lookup answers `deleted`, and `PUT /api/v1/contents/{sha256}` answers 409 before it reads the body, so no collector brings the document back, while a browser, token, or mail upload of the bytes archives them again, because a person chose to. The rendering step of a stored email digests the printed PDF and claims it the same way. `original_sha256` is null for documents archived before migration 0006 until the scheduled backfill digests them, and while any document of an accepted kind lacks it, `POST /api/v1/contents/lookup` and `PUT /api/v1/contents/{sha256}` answer 503 with `Retry-After: 900`, because the lookup would call those bytes absent and a collector would archive them a second time. A document whose original R2 lacks therefore keeps both routes closed until a member deletes it, and the `Scheduled content digests:` line names it. `documents_original_sha256_index` keeps that check from scanning the archive. Identity is the bytes alone, never the name, the path, or a date, so another scan of the same paper is another content.
- **Moondream reads stored pixels.** It ignores the EXIF orientation, so a phone photograph reaches it sideways and it repeats text until its token limit. `normalizeRecognitionImage` sends every uploaded image through `IMAGE_TRANSFORMER`, which applies the orientation. Cloudflare Images returned transparent pixels as black for JPEG output until the output stated `background: "#FFFFFF"`. The local simulation of the binding supports only width, height, rotate, and format, so it is remote in development.
- **A page that hits the token limit is read at all four rotations.** `recognizePage` reads the other three rotations in parallel workflow steps and keeps the reading with the most distinct words, counted with `Intl.Segmenter` so that scripts without spaces work. It records the winner in `recognition_quarter_turns`, and later pages start from that rotation. A document fails with `unreadable_page` only when no rotation finishes.
- **`cf dev` needs a Cloudflare login.** `AI_RUNTIME`, `BROWSER_RENDERER`, `IMAGE_TRANSFORMER`, and `SEARCH_INDEX` are remote in development, so `cf dev` opens a remote preview session on the signed-in account. It deploys nothing.
- **What the owner's development server can reach.** `cf` authenticates there through a restricted API token in the `CLOUDFLARE_API_TOKEN` variable of the owner's shell, and `cf auth whoami` names that source. Never read, print, or search for the token or the file that sets it. The permission check refuses such a command. The owner allows `pnpm dev` and deploys to staging, and the `schublade.deploy.json` on that server describes the staging Worker. Measured on 2026-11-17:
  - It works for `pnpm dev` with every remote binding. A digital PDF, a photographed receipt, and a scanned receipt all reached archived, with a title and `indexed_at`, through Moondream, Images, AI Gateway, classification, and AI Search. `pnpm run deploy` deploys the development and staging Workers, and only those. The staging database answers `cf d1 raw` and `cf d1 migrations list` and `apply`. `cf ai-gateway logs list --gateway-id <identifier>` and `cf o11y telemetry` queries answer as well.
  - It is refused for R2 listings (`cf r2 buckets list` and `cf r2 objects list --bucket-name <name>` answer 10000) and for KV (`cf kv namespaces list` answers 10000).
  - Access rights come and go. The owner grants "Access: Apps" for a change and removes it afterwards. Without it, `cf zero-trust access applications list` answers an empty list although staging sits behind Access, so an empty list never means that no application exists.
  - So `pnpm run provision` must not run there. It finds R2 and KV resources by listing them, and an empty Access listing would make it create applications. Apply a new migration with `cf d1 migrations apply <database identifier> --dir drizzle`, which targets the remote database unless `--local` is given, before the deploy whose code needs it, never after.
  - To change an Access application, ask the owner for "Access: Apps" with Edit. Read the application with `cf zero-trust access applications get <identifier>`. Build its body with `accessApplicationBody` from `scripts/provisioning_requests.ts`, so it matches what provisioning writes. Send it with `cf zero-trust access applications update <identifier> --body <json>`, then read it back. On 2026-11-17 this added `/api/v1` to "schublade schublade-staging: token ingestion". Afterwards an unauthenticated POST to `/api/v1/contents/lookup` reached the Worker, and `/settings` still redirected to the Access login.
  - Staging sits behind Access, which an agent cannot pass. Its bearer token routes take the staging ingest token in `~/.config/schublade/staging_ingest_token`, a file only the owner's user can read. Pass it as `-H "Authorization: Bearer $(cat ~/.config/schublade/staging_ingest_token)"` and never print it. On 2026-11-17 it answered lookup, a 202 then 200 upload of the same bytes, and a 422 for a wrong digest on staging. It permits uploads to staging only: its level is `ingest`, so `/api/v1/changes` and the representations answer it 403.
  - In a git worktree under `.claude/worktrees/`, `cf dev` failed with "it's necessary to set a CLOUDFLARE_API_TOKEN environment variable", while the main checkout found the token. This is one more reason to work in the main checkout.
  - Another program on that server can hold port 3000. Vite then serves on 3001, and `pnpm evaluate:extraction` and `pnpm evaluate:search` need `--base-url http://localhost:3001`.
  - `cf dev` printed `Error: internal error; reference = …` three times while two uploads archived normally, with no error span in the local explorer's observability tables. The cause is unknown.
- **Local development runs as `schublade-development`.** The remote preview of a Worker that shares a deployed name sits behind that deployment's Access application and fails without a service token. `cloudflare.config.ts` therefore names the Worker `schublade-development` in every local mode, and `pnpm evaluate:extraction` addresses the local Workflow under that name. Never provision an environment with that worker name.
- **Local development does not run the Cron Trigger.** Every 15 minutes a deployed Worker starts up to 20 emails still awaiting rendering and runs the scheduled backfill, which uploads up to 100 archived documents that AI Search lacks, failed to index, or holds a stale revision of, and logs one `Scheduled search indexing:` line. It also digests up to 25 documents whose `original_sha256` is null, passing over those it cannot read, and logs one `Scheduled content digests:` line. To run it once on a dev server, request `http://localhost:3000/cdn-cgi/local/scheduled?format=json`. It lists and uploads into the billed development instance.
- **Only `/api/documents/ingest`, the eight client routes under `/api/v1`, and the OAuth paths skip Access.** `request_dispatch.ts` compares the exact pathname with the token ingestion path, matches the anchored patterns of the route table in `client_paths.ts` (`GET /api/v1/authorization`, `GET /api/v1/changes`, `GET /api/v1/documents/<uuid>/original`, `/text`, and `/thumbnail`, `POST /api/v1/contents/lookup`, `PUT /api/v1/contents/<64 lowercase hex>`, `GET /api/v1/documents/<uuid>`), and compares with `ACCESS_BYPASSING_PATHS`. Access bypasses those paths through the applications "schublade <worker>: token ingestion", whose destinations `tokenIngestionDestinations` names, and "schublade <worker>: model context protocol", whose destinations `ACCESS_BYPASS_DESTINATIONS` names. Subpaths inherit the bypass, so the Worker keeps every path it does not know behind `requireAccess`, a trailing slash, uppercase hexadecimal, another case, an extra segment, or `/api/v1/x` included. A new route is one entry of that table, which cannot omit its method or level. The consent page at `/authorize` stays behind Access. Never widen a comparison to a prefix or loosen a pattern; `request_dispatch.workerd.test.ts` fails when you do.
- **A token adds documents, or reads and adds, and reading is never the default.** The levels are ordered `ingest`, `read`, `modify`, `administer`, by how much of the household's papers each exposes, and each grants the levels before it. An `ingest` token is for a scanner, a script, or a Shortcut: it reaches `/api/documents/ingest`, the three collector routes, and `GET /api/v1/authorization`, and it reads no title, text, or original. A `read` token is for the Schublade app and also reads `/api/v1/changes` and the three representations. Settings issues both and starts with `ingest`. Never lower a route's level in `client_paths.ts` to make a token work; issue a `read` token instead. One test in `request_dispatch.workerd.test.ts` lists every route of the table with what a token of each level gets, so a new route or a changed level fails it until its line says what is meant.
- **A restricted scope is applied or refused, never ignored.** Each route of `client_paths.ts` states `restrictedScope`. The authorization, the changes, and the representations apply the scope. The three collector routes and `/api/documents/ingest` refuse a token whose scope holds a list with 403, because a collector must see every content and an upload answers the identifier of a document that holds the bytes already. A new route that answers anything about a document either passes the scope to its query or refuses.
- **Only `If-None-Match` makes a representation answer without a body.** `representation_requests.ts` passes that header alone to R2 and ignores every other precondition and `Range`, because R2 answers any failed precondition without a body and the route would call that 304. An original with a recorded digest answers 304 only after `head` found the file, so a lost file is never called current.
- **A thumbnail that cannot be drawn leaves a mark.** `readThumbnail` writes an empty object with the metadata `thumbnail: unrenderable` at the thumbnail's key when PDFium fails, and for a day a request reads that mark and not the original. Code that reads `thumbnail.png` from R2 must expect the mark.
- **`/mcp` is stateless and read-only.** `McpAgent` is deprecated in `agents` 0.33, so `archive_tools.ts` builds an `McpServer` for each request through `createMcpHandler` from `agents/mcp/server`, and no Durable Object takes part. `@modelcontextprotocol/server` stays at the exact version that the installed `agents` release names as its peer.
- **D1 decides whether a grant stands, and every tool must pass the scope.** `@cloudflare/workers-oauth-provider` requires the binding name `OAUTH_KV` and keeps clients and tokens there, but KV is eventually consistent, so a refresh at a location that still caches a deleted grant writes it back. `authorization_grants` therefore holds the scope and `revoked_at`, the token carries only the row identifier in its `props`, and `serveArchiveTools` reads that row on every request. Disconnecting a client leaves its KV tokens to expire. Scope lists hold record identifiers, so a rename leaves a grant intact, and they bind as one JSON parameter through `json_each`, because D1 allows 100 bound parameters per query. A query without `authorizationScope` reads the whole archive, so a new tool passes it to every query. A merge deletes the tag it folds away, so a scope whose denied tag no longer exists admits nothing, and each scoped statement asks that itself.
- **`cf dev` can scramble a large remote response.** In local runs, the PDF from the remote `BROWSER_RENDERER` binding reached the Worker with 8 KiB chunks out of order in 3 of 4 renderings, which shifted its objects by multiples of 8192 bytes. The same request through `cf browser-run quick-action pdf` was intact. PDFium repairs such a file, but PDF.js and `toMarkdown` then read some fonts as text such as `6XEMHFW` for `Subject`. `pdftotext` warns about the cross-reference table of such a file, so check that before suspecting the markup.
- **Mail markup is made inert before printing.** `printMail` removes scripts, `noscript`, frames, refresh tags, and `<base>` with `HTMLRewriter`, because `allowResourceTypes` must include `document` or Browser Run prints a blank page, and a frame is a document too. It repeats until the output stops changing, because removing a tag can join the text around it into a new tag. `HTMLRewriter` exists only in workerd, so `mail_rendering.ts` is tested there.
- **`toMarkdown()` can keep only part of a tagged PDF.** Chromium prints tagged PDFs. On a forwarded email, `toMarkdown()` kept the three header lines of page 1, dropped the layout tables below them, and returned page 2 empty, while PDFium read both pages in full. A complete conversion held every letter and digit of the text layer on all 27 digital pages of the test documents, so `selectPageTextSources` takes a converted section only when it holds at least 90% of a readable text layer. A printed email skips the conversion, because Chromium wrote its text layer from the HTML. Converting that HTML to Markdown instead gave 95% tracking URLs and collapsed the layout tables into one row.
- **Every table is journaled or listed as not replicated.** Triggers on the seven tables of `journaledTables` in `schema.ts` move a record's entry in `change_journal`, and `tablesNotReplicated` names every other table. A new table goes into one of the two lists, and a copied one gets its three triggers in a custom migration, as `0009_journal_record_changes.sql` has them, and an insert, an update, and a delete in `writesOfEachTable` in `change_journal.workerd.test.ts`, which fails otherwise. Never write `INSERT OR REPLACE` or `REPLACE INTO`: D1 runs with `recursive_triggers` off, so the row a REPLACE deletes fires no delete trigger and a client keeps it for good, and `pnpm lint` rejects both.
- **A migration that rebuilds a journaled table drops its triggers.** SQLite drops a table's triggers with the table, so a migration that recreates one, as drizzle-kit does for many column changes, must create its three triggers again. `change_journal.workerd.test.ts` catches the omission.
- **Migrations 0008 and 0009 come before the deploy that reads the journal.** Apply them to a deployed database with `cf d1 migrations apply <database identifier> --dir drizzle` first, because `/api/v1/authorization` and `/api/v1/changes` read `change_journal_identity` and `change_journal`.

- **The manifest link needs `crossOrigin: "use-credentials"`.** Access protects `public/` like everything else, and a browser sends no cookie for a manifest without that attribute.

- **A page never sizes the window.** A constraint inside the window that outranks 500, the priority at which the window keeps its size, resizes the window to fit; the folder page's column once shrank the window to 1,017 points. Give a preferred width or height inside a page a priority below 500, as `PageColumnView` does.
- **The renderer waits for quiet, not for a fixed time.** `InterfaceRenderer` builds the real workspace and lets it load through `RendererLibraryQueries`, which counts its calls. A capture waits until no call was asked or answered for 300 ms, so a picture decoded after its answer is drawn. Never set a screen's state by hand in the renderer: the real loads overwrite it a moment later.
- **Releases are signed and notarized only in the build account.** `iosbuild` holds the Developer ID Application identity in its own keychain, which `~/.zshenv` unlocks for every SSH session, and an App Store Connect team key (App Manager) in `ASC_KEY_ID`, `ASC_ISSUER_ID`, and `ASC_PRIVATE_KEY_PATH`. Its `configuration/local_signing.xcconfig` names the identity, and the runner's rsync keeps that git-ignored file. Nothing that holds the key or the certificate comes to the server; the setup is in the devbox repository's README. A notarization is a release, so run `release_application.sh` only when the user asks. When the notary service answers `Invalid`, `ssh mac 'xcrun notarytool log <id> --key "$ASC_PRIVATE_KEY_PATH" --key-id "$ASC_KEY_ID" --issuer "$ASC_ISSUER_ID"'` names the problem. The zip stays on the Mac; `scp mac:schublade/native_client/macintosh_application/build/Schublade.zip .` fetches it. The Mac application sets no version number yet.
- **The Mac runner copies the tree at launch.** `scripts/execute_on_macintosh.sh` rsyncs what git tracks before it runs the command, so a file written after the launch is not on the Mac, and `cargo fmt --check` there judges the copy, not your working tree.

## Documentation lookup order

1. `cf docs search "<question>"` returns ranked documentation pages. Fetch a page with `Accept: text/markdown`.
2. `cf cli search "<task>"` finds a `cf` command. Run `<command> --help` for its flags and `cf schema <command>` for the API request it sends.
3. `https://developers.cloudflare.com/<product>/llms.txt` indexes a product, and appending `index.md` to a page URL returns it as Markdown.
4. The type declarations in `node_modules`, such as `cf/config` for the binding builders.

Keep `cf cli search` and `cf docs search` queries anonymous. Describe the action and the resource type, never names, identifiers, domains, or tokens.
